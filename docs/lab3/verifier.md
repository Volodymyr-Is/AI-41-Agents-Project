# Верифікатор на іншій моделі як остання брама

- **Workflow:** `.github/workflows/gates.yml` (задача `verify`)
- **Порядок ланцюга:** `types` → `lint` → `tests` → `build` → `verify` → `record`
- **Команда перевірки:** `npm run verify` (`tsx scripts/harness/verify-task-cli.ts`)

---

## 1. Місце в ланцюзі

- **Детерміновані брами (крок 01):** `types` (5 хв), `lint` (5 хв), `tests` (10 хв), `build` (15 хв).
- **Верифікатор запускається лише після них:** задача `verify` у workflow має явну залежність `needs: build`. Завдяки стандартній поведінці GitHub Actions (неявна функція статусу `success()`), на будь-якій червоній або пропущеній детермінованій брамі верифікатор навіть не запускається.
- **Економія ресурсів:** у Кроці 01 на гілці `harness/red-2026-10-28` брама `types` впала за 12 секунд. Завдяки ланцюгу залежностей, верифікатор взагалі не викликався — це зберегло виклики API та час раннера, оскільки синтаксично чи структурно зламаний код не має потрапляти до моделі-судді.

---

## 2. Конфігурація

- **Модель, що виконувала задачу (виконавець):** `nvidia/nemotron-3.5-lightning:free` / `cohere/north-mini-code:free` (OpenRouter, родина Nemotron/Command).
- **Модель верифікатора (суддя):** `gemini-3.8-flash` (Google AI Studio, родина Gemini).
- **Шлях і його ціна:** безкоштовний рівень Google AI Studio API (`GEMINI_API_KEY`), вартість: **$0.00** (generous free-of-charge quota).
- **Незалежність родин:** використання моделі Gemini для перевірки коду, згенерованого Nemotron, повністю усуває упередження самооцінювання (*self-preference bias*).
- **Умова блокування:** суворе блокування за `isBlocked(report)` — якщо хоча б один критерій має вердикт `fail` або `unknown`, зміна блокується і вихідний код процесу стає ненульовим (`exit 1`). Статус `unknown` вважається аварійним і не допускається до злиття.

---

## 3. Рубрика — один запит на один критерій

Суддя викликається за принципом «один суддя — один вимір»: кожен критерій оцінюється в окремому ізольованому запиті з чіткою рубрикою.

| Критерій задачі | Що питаємо суддю (дослівно) | Що вважається evidence | Що означає unknown |
|---|---|---|---|
| **crit-export** | Чи експортована головна функція/модуль з повною статичною типізацією аргументів і результату? | Точний рядок `export function` або `export const` із сигнатурою типів | Відсутній файл модуля або експорт неможливо локалізувати |
| **crit-logic** | Чи відповідає реалізована формула/алгоритм вхідним математичним або бізнес-вимогам? | Конкретні рядки коду з операціями розрахунку | Логіку не реалізовано або вона прихована у зовнішніх викликах |
| **crit-validation** | Чи реалізовано захист від некоректних/від'ємних значень (throw Error / Zod schema)? | Умовні конструкції `if (...) throw` або правила валідації `.refine()` / `.min()` | Відсутні будь-які перевірки граничних значень в артефакті |
| **crit-tests** | Чи містить тестовий файл юніт-тести Vitest на позитивні та граничні сценарії? | Блоки `describe` / `it` з викликами `expect(...)` у каталозі `tests/` | Файл тестів відсутній або містить порожні заглушки |

## 4. Калібрування (10 власноруч розмічених випадків)

Для перевірки надійності та узгодженості судді було проведено калібрування на 10 випадках, що охоплюють завдання спортивного журналу (`t-01` – `t-06`).

| № | Задача / артефакт | Критерій | Мій вердикт | Вердикт судді | Збіг |
|---|---|---|---|---|:---:|
| 1 | `t-01` (MET калорії) | `crit-export-met` (експорт функції з типами) | pass | pass | ТАК |
| 2 | `t-01` (MET калорії) | `crit-formula-met` (формула розрахунку та округлення) | pass | pass | ТАК |
| 3 | `t-01` (MET калорії) | `crit-validate-met` (перевірка додатних значень) | pass | pass | ТАК |
| 4 | `t-01` (MET калорії) | `crit-tests-met` (наявність юніт-тестів) | pass | pass | ТАК |
| 5 | `t-02` (Пульсові зони) | `crit-hr-schema` (Zod-схема зон пульсу 1-5, 40-220 bpm) | pass | pass | ТАК |
| 6 | `t-03` (Тоннаж) | `crit-tonnage-formula` (помилка: додавання замість множення) | fail | fail | ТАК |
| 7 | `t-03` (Тоннаж) | `crit-tonnage-negatives` (відсутність валідації від'ємних значень) | fail | unknown | НІ |
| 8 | `t-04` (Темп бігу) | `crit-pace-format` (пропущено форматування часу MM:SS) | fail | fail | ТАК |
| 9 | `t-05` (HRR відновлення) | `crit-hrr-thresholds` (артефакт містить лише TODO заглушку) | unknown | unknown | ТАК |
| 10 | `t-06` (Тривалість) | `crit-duration-to-seconds` (функцію пропущено в коміті) | unknown | unknown | ТАК |

### Метрики узгодженості:
- **Кількість випадків ($n$):** 10
- **Сира згода ($P_o$):** **90.0%** (0.9000, 9 збігів із 10)
- **Очікувана випадкова згода ($P_e$):** **37.0%** (0.3700)
- **Каппа Коена ($\kappa$):** **0.8413** *(розраховано у `scripts/harness/calibrate.ts` за формулою $\kappa = \frac{P_o - P_e}{1 - P_e}$)*

### Матриця невідповідностей:

| Людина \ Суддя | pass | fail | unknown | Всього (людина) |
|---|:---:|:---:|:---:|:---:|
| **pass** | **5** | 0 | 0 | 5 |
| **fail** | 0 | **2** | 1 | 3 |
| **unknown** | 0 | 0 | **2** | 2 |
| **Всього (суддя)** | 5 | 2 | 3 | **10** |

### Аналіз розбіжностей:
- **Де розійшлися:** випадок №7 (`crit-tonnage-negatives`). Людина поставила `fail`, оскільки перевірила відсутність валідації в коді, а суддя через мережевий таймаут підключення звернувся до аварійного fallback і повернув `unknown`.
- **Безпековий висновок:** обидва вердикти (`fail` та `unknown`) у нашому харнесі **блокують злиття**. Жоден сумнівний або непройденний критерій не отримав хибного `pass`.
- **Що покращено:** у функцію виклику судді `callJudge` додано автоматичний повтор спроби (retry) з паузою 1.5 с, що усуває подібні помилки з'єднання при подальших прогонах.

## 5. Чесні обмеження

1. **Обмеженість вибірки:** 10 випадків — це встановлений курсом мінімум для калібрування рубрики, а не повноцінна статистична репрезентація всіх можливих помилок програмування.
2. **Контекстна залежність:** каппа $\kappa = 0.8413$ розрахована для набору задач спортивного журналу. Згідно з дослідженнями (Norman та ін., 2026), якість суддів може суттєво варіюватися на бенчмарках іншого профілю.
3. **Що суддя точно НЕ перевіряє:**
   - Швидкодію алгоритмів та споживання пам'яті (runtime performance).
   - Візуальну коректність інтерфейсу та адаптивність CSS.
   - Стійкість до специфічних race conditions у багатопотоковому середовищі.
   Саме тому верифікатор стоїть **останнім**, а не першим.

## 6. Верифікатор зупинив зміну (Stop Gate)

Для перевірки реальної зупинки верифікатором було протестовано випадок `t-03` (розрахунок тренувального тоннажу), де синтаксичні перевірки та лінтер проходили успішно, але бізнес-вимога була порушена.

- **Артефакт зупинки:** [`docs/lab3/verdicts/stop-case-verdict.json`](verdicts/stop-case-verdict.json)
- **Дослівний вердикт зупинки:**
  ```json
  {
    "id": "crit-tonnage-formula",
    "verdict": "fail",
    "reason": "Формула розрахунку тоннажу помилкова: використовується оператор додавання reps + weightKg замість добутку reps * weightKg",
    "evidence": "src/utils/volume-load.ts:4: return sets.reduce((acc, s) => acc + s.reps + s.weightKg, 0);"
  }
  ```
- **Результат:** скрипт `verify-task-cli.ts` завершився з кодом `exit 1` та вивів повідомлення:
  `[БЛОКУВАННЯ ЗЛИТТЯ]: Верифікатор відхилив зміну! Не всі критерії мають статус "pass".`
- **Виправлення коду:**
  Заміна рядка на `return sets.reduce((acc, s) => acc + s.reps * s.weightKg, 0);` та додавання валідації `if (s.reps < 0 || s.weightKg < 0) throw new Error(...)`.
- **Повторний успішний вердикт:** [`docs/lab3/verdicts/t-01-verdict.json`](verdicts/t-01-verdict.json), де всі 4 критерії отримали `pass`, а вихідний код склав `exit 0`.
