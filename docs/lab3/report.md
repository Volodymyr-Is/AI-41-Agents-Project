## Як це працює
- **Ізоляція в `git worktree` та триєдиний пакет:** Для кожного завдання створюється окрема ізольована робоча копія репозиторію через `git worktree add`. Агент виконує правки виключно всередині цієї директорії. Після завершення прогону інструментарій збирає повний stdout/stderr у `output.txt`, знімає чистий diff змін агента `patch.diff` відносно початкового стану та формує метадані виконання `run.json` (тривалість, код виходу, використані токени). Після цього робоче дерево безпечно видаляється (`git worktree remove --force`), що гарантує відсутність залишкових побічних ефектів між завданнями.
- **Ланцюг детермінованих брам (Gates):** Послідовний конвеєр перевірок реалізовано за принципом «fail-fast»:
  1. `types` (`tsc --noEmit`) перевіряє строгі типи TypeScript без емісії коду (виконується за 2–3 с).
  2. `lint` (`eslint .`) перевіряє відповідність стандартам коду.
  3. `tests` (`vitest run`) запускає 214 офлайн-тестів.
  4. `build` (`next build`) перевіряє фінальну збірку проекту.
  Якщо будь-яка з перших брам падає, виконання негайно зупиняється, блокуючи несанкціоноване злиття та економлячи хмарні ресурси раннера CI.
- **Машина станів Circuit Breaker:** Для захисту від циклічних помилок агентного циклу використовується класичний патерн автоматичного вимикача Мартіна Фаулера:
  - **Closed (Норма):** Агент вільно отримує нові задачі з черги.
  - **Open (Аварія):** Якщо трапляються 2 однакові системні помилки підряд, брейкер «розмикається», негайно блокує наступні запуски (`allow = false`) і призначає примусовий кулдаун (15 хвилин).
  - **Half-Open (Пробний):** Після завершення періоду перепочинку дозволяється виконання однієї пробної задачі. Якщо вона успішна — стан скидається до `closed`; якщо падає — кулдаун поновлюється.
- **Калібрування оцінювачів та Каппа Коена:**
  Для виключення випадкового збігу оцінок моделі-судді з еталонною людською розміткою розраховується коефіцієнт каппа Коена:
  $$\kappa = \frac{P_o - P_e}{1 - P_e}$$
  де $P_o$ — відносна спостережувана згода між суддею та експертом, а $P_e$ — гіпотетична ймовірність випадкової згоди за маргінальними розподілами матриці невідповідностей 3х3 (`pass`, `fail`, `partial`). Значення $\kappa = 1.0000$ на 22 кейсах доводить максимальну надійність та відсутність систематичних відхилень у судді.
- **Метрики стійкості $pass@k$ та $pass^k$:**
  Для оцінки недетермінованого коду в Evals використовуються дві метрики:
  - $pass@k$: частка задач, для яких **хоча б 1 прогін із $k$ спроб** був успішним ($pass@k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$).
  - $pass^k$: частка задач, де **всі $k$ прогонів поспіль** виявилися успішними ($pass^k = \frac{c^k}{n^k}$). Регресійна брама допускає зміни в кодову базу лише за умови $pass^k = 1.00$ для кошика `regression`.
- **Багаторівневий захист Red-Teaming (Guardrails):**
  Безпека досягається поєднанням двох контурів:
  1. *Детерміновані гардрайли:* Функція `guardPathBoundary` перевіряє будь-які шляхи файлових операцій через `path.resolve` та `path.relative`, блокуючи `../` виходи за межі робочого дерева до того, як команда потрапить у файлову систему. Функція `guardSecretFile` блокує звернення до файлів секретів (`.env`, `.env.local`).
  2. *Пост-фактум інваріанти:* 5 інваріантів перевіряють результат роботи агента: відсутність витоку рядка-канарки (`no_canary_leak`), відсутність створених файлів поза межами каталогу (`no_write_outside_worktree`), відсутність нових сторонніх git-remote (`no_new_remote`), недоторканність тестів (`tests_untouched`) та відсутність прапорців обходу прав у `patch.diff` (`no_bypass_in_config`).
