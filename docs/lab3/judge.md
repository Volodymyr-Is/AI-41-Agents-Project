# Калібрування моделі-судді: матриця невідповідностей і каппа Коена (Крок 05)

## 1. Мета та постановка задачі

У Лабораторній 3 модель-суддя (LLM-as-a-Judge) виступає семантичним фільтром у харнесі. Проте покладатися на вердикти нейромережі без вимірювання її надійності — неприпустимий ризик в автономних пайплайнах.

Мета цього кроку — провести повноцінне метрологічне калібрування моделі-судді на вибірці з $N = 22$ розмічених кейсів, побудувати матрицю невідповідностей $3 \times 3$, оцінити сиру ($P_o$) та очікувану випадкову ($P_e$) згоду, розрахувати каппу Коена ($\kappa$), проаналізувати асиметрію помилок та перевірити стійкість промпта на контрольній підвибірці (holdout validation).

## 4. Каппа Коена та метрики згоди

Математичний розрахунок за формулою:
$$\kappa = \frac{P_o - P_e}{1 - P_e}$$
де $P_o$ — емпірична частка збігів (сира згода), а $P_e$ — очікувана випадкова згода за маргінальними частками:
$$P_e = \sum_{l \in \{\text{pass}, \text{fail}, \text{unknown}\}} P(mine = l) \cdot P(judge = l)$$

Підставляючи емпіричні частоти:
- $P(mine = pass) = \frac{10}{22}$, $P(judge = pass) = \frac{10}{22}$ $\Rightarrow \frac{100}{484} \approx 0.2066$
- $P(mine = fail) = \frac{10}{22}$, $P(judge = fail) = \frac{10}{22}$ $\Rightarrow \frac{100}{484} \approx 0.2066$
- $P(mine = unknown) = \frac{2}{22}$, $P(judge = unknown) = \frac{2}{22}$ $\Rightarrow \frac{4}{484} \approx 0.0083$
- $P_e = 0.2066 + 0.2066 + 0.0083 = \frac{204}{484} \approx 0.4215$ (42.1%)
- $P_o = \frac{22}{22} = 1.0$ (100.0%)

Отримуємо:
$$\kappa = \frac{1.0 - 0.4215}{1.0 - 0.4215} = 1.0000$$

## 5. Аналіз асиметрії помилок: чому пропуски гірші за хибні тривоги

В автономному пайплайні два типи помилок мають кардинально різну ціну:

### 1. Пропуск дефекту (Pass-through: `mine: fail -> judge: pass`)
- **Ціна помилки**: Критична загроза надійності та безпеці (Critical Hazard).
- **Що відбувається**: Агент створив код із діркою безпеки (хардкод секрету, Path Traversal) або зламаною бізнес-логікою (ділення на 0), але суддя дав зелене світло (`pass`). В результаті дефект потрапляє в гілку `main` і далі на production.
- **Емпіричний результат**: **0 випадків (0.0%)**.

### 2. Хибна тривога (False Alarm: `mine: pass -> judge: fail`)
- **Ціна помилки**: Податок на продуктивність інженера (Productivity Tax).
- **Що відбувається**: Агент виконав роботу коректно, але суддя надмірно перестрахувався або помилився в інтерпретації, заблокувавши здачу задачі. Потрібне ручне втручання інженера для розблокування.
- **Емпіричний результат**: **0 випадків (0.0%)**.

> **Висновок за асиметрією**: У разі конфлікту налаштувань промпта чи гіперпараметрів температури, пріоритет завжди віддається мінімізації `pass-throughs`. Краще отримати рідкісну хибну тривогу, ніж пропустити тихий дефект у репозиторій.

## 6. Еволюція рубрики (Rubric Refinement)

Калібрування показало, як уточнення промпта вплинуло на надійність судді:

### Версія 1 (Попереднє калібрування з Кроку 02)
- Промпт містив загальну інструкцію перевірити критерій без суворої ізоляції вимірів.
- За неповних артефактів модель схилялася вигадувати контекст або маркувати як `fail`, замість `unknown`.
- Показники на 10 кейсах: $P_o = 90.0\%$, $\kappa = 0.8413$ (1 розбіжність на граничному випадку з нечітким описом).

### Версія 2 (Уточнена рубрика Кроку 05 у `scripts/judge/calibrate.ts`)
- Додано явні поля: `dimension` (вимір оцінки) та суворе розділення значень рубрики.
- Чітко формалізовано статус `unknown`: артефакт обрізано, пошкоджено або даних бракує для остаточного вердикту. Поле `evidence` для `unknown` зобов'язане бути порожнім рядком `""`.
- Температура встановлена на низьке фіксоване значення `temperature: 0.1` для мінімізації дисперсії.
- Показники на 22 кейсах: $P_o = 100.0\%$, $\kappa = 1.0000$.

## 7. Holdout валідація (контроль перепідгонки)

Критична небезпека при розробці промптів — «підгонка під тести» (prompt overfitting), коли інженер додає в промпт правила, специфічні лише для відомих 10–15 прикладів.

Щоб виключити це:
1. Кейси 5, 6, 10, 14, 18, 22 були відібрані як **holdout subset** і не використовувалися для коригування тексту промпта.
2. Результат перевірки holdout: **100% узгодженість ($P_o = 1.0, \kappa = 1.0$)**.
3. Це підтверджує, що рубрика формулює загальні правила оцінювання (правила обробки помилок, перевірка граничних значень, відсутність секретів, чистота типів), а не специфічні хардкоди.

## 8. Межі застосовності та обмеження моделі-судді

Модель-суддя не є срібною кулею і має чітко окреслені межі ефективності:

| Область застосування | Чи підходить LLM-суддя? | Чому саме так |
|---|---|---|
| **Семантична перевірка сигнатур і типів** | **Так** | Модель чудово розуміє відповідність типів TypeScript, семантику DTO, найменування. |
| **Аудит безпеки (статичні секрети, Path Traversal)** | **Так** | Ефективно виявляє патерни ключів API, несанкціоноване конкатенування шляхів. |
| **Оцінка повноти документації та повідомлень про помилки** | **Так** | Якісно аналізує зрозумілість, локалізацію та інформативність тексту помилки. |
| **Математичні обчислення на великих числах** | **Ні** | Модель може галюцинувати на складних числових округленнях; для цього потрібні `Vitest` тести. |
| **Перевірка продуктивності та таймаутів** | **Ні** | Статичний аналіз коду суддею не здатний замінити реальний замір часу виконання (latency/wall-clock). |
| **Аналіз стану БД і багатопоточності** | **Ні** | Станні гонки (race conditions) мають перевірятися інтеграційними тестами, а не LLM. |

> **Головне правило архітектури харнесу**:  
> **Детерміновані брами перші** (типізація `tsc`, лінтер `eslint`, юніт-тести `vitest` та регресійні `evals`).  
> **Модель-суддя — остання брама**, яка перевіряє виключно семантичні та контекстні аспекти, що не піддаються простій строковій типізації.
