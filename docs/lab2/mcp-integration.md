# Інтеграція MCP-сервера: Агент кодування та Застосунок

Автор: Ісаєнко Володимир Андрійович · Дата: 20.10.2026 · Версія: v1.0.0

## 1. Мета та архітектура інтеграції

Згідно з вимогами Кроку 09 лабораторної роботи, власний MCP-сервер спортивного щоденника `sports-journal-mcp` вважається робочим лише тоді, коли його інструменти викликано з **двох різних боків**:
1. **З боку агента кодування** (Antigravity / Cursor / Claude Code) — для інтелектуального дослідження кодової бази та нормативів під час програмування.
2. **З боку кінцевого застосунку** («Спортивний журнал») — для обслуговування запитів спортсмена, обчислення цільових зон навантаження та формування порад із обов'язковим цитуванням джерел `[doc-XX]`.

Обидві конфігурації закомічені в репозиторій **без секретів та API-ключів**.

## 2. Підключення 1: Агент кодування (Coding Agent)

### 2.1. Конфігурація підключення
Конфігурація для агентів кодування зберігається у корені репозиторію в файлі [`.mcp-config.json`](file:///c:/Users/volod/OneDrive/Документи/GitHub/AI-41-Agents-Project/.mcp-config.json):

```json
{
  "mcpServers": {
    "sports-journal": {
      "command": "npx",
      "args": ["tsx", "src/mcp/server.ts"],
      "env": {}
    }
  }
}
```

- **Тип транспорту**: `stdio` (стандартне введення/виведення через дочірній процес Node.js).
- **Команда запуску**: `npx tsx src/mcp/server.ts`.
- **Безпека**: файл не містить жодних ключів чи чутливих змінних оточення (`env: {}`).

### 2.2. Сценарій виклику та спосіб взаємодії
Агент кодування під час дослідження логіки спортивного щоденника:
1. Виконує запит `tools/list` та виявляє інструменти `search_knowledge_base` і `get_document_by_id`.
2. Робить `tools/call` до `search_knowledge_base` із запитом `query: "періодизація навантажень мезоцикли"`, отримуючи відповідні чанки зі статті `doc-05`.
3. Робить `tools/call` до `get_document_by_id` із `id: "doc-05"`, отримуючи повний текст методичних рекомендацій для подальшого аналізу.

### 2.3. Доказ фактичного виклику (Траса)
- **Файл траси**: [`docs/lab2/traces/mcp-agent-call.json`](file:///c:/Users/volod/OneDrive/Документи/GitHub/AI-41-Agents-Project/docs/lab2/traces/mcp-agent-call.json).
- **Команда відтворення**: `npm run mcp:agent-demo` (або `npx tsx scripts/mcp-agent-runner.ts`).
- **Ключові метрики виклику**:
  - Час підключення: 1188 мс.
  - Виклик `tools/list`: 5 мс (виявлено 2 інструменти).
  - Виклик `search_knowledge_base`: 5 мс (знайдено 2 релевантні фрагменти `doc-05#chunk-1` та `doc-05#chunk-0` з оцінкою RRF 0.0164).
  - Виклик `get_document_by_id`: 5 мс (отримано повний текст `doc-05`).

## 3. Підключення 2: Застосунок «Спортивний журнал» (Application)

### 3.1. Конфігурація підключення
Конфігурація застосунку розташована у [`src/mcp/app-config.json`](file:///c:/Users/volod/OneDrive/Документи/GitHub/AI-41-Agents-Project/src/mcp/app-config.json):

```json
{
  "server": {
    "name": "sports-journal-mcp",
    "transport": "stdio",
    "command": "npx",
    "args": ["tsx", "src/mcp/server.ts"]
  },
  "client": {
    "name": "sports-journal-app",
    "version": "1.0.0"
  },
  "timeouts": {
    "requestTimeoutMs": 15000,
    "spawnTimeoutMs": 5000
  }
}
```

- **Реалізація клієнта**: типізований клієнт [`src/mcp/app-client.ts`](file:///c:/Users/volod/OneDrive/Документи/GitHub/AI-41-Agents-Project/src/mcp/app-client.ts) на базі `@modelcontextprotocol/client`.
- **Безпека**: секрети відсутні, параметри таймаутів визначені локально.

### 3.2. Сценарій користувача в застосунку
- **Користувач**: Атлет, який заповнює план тренування в щоденнику.
- **Запит**: «Як правильно розрахувати пульсові зони за формулою Карвонена?».
- **Логіка роботи застосунку**:
  1. Клієнт підключається до MCP-сервера через `SportsJournalAppClient.connect()`.
  2. Застосунок викликає `searchKnowledgeBase('формула Карвонена пульсові зони', 2)`.
  3. Сервер повертає чанки з `[doc-02]` та формулою $ЧСС_{цільова} = ((ЧСС_{макс} - ЧСС_{спокою}) \times \%інтенсивності) + ЧСС_{спокою}$.
  4. Застосунок завантажує повний норматив через `getDocumentById('doc-02')`.
  5. Застосунок формує картку тренувальної поради з обов'язковим зазначенням цитати `[doc-02]`.

### 3.3. Доказ фактичного виклику (Траса)

- **Команда відтворення**: `npm run mcp:app-demo` (або `npx tsx scripts/mcp-app-runner.ts`).
- **Ключові метрики виклику**:
  - `tools/list`: 2 інструменти зареєстровано.
  - `search_knowledge_base`: 5 мс (знайдено 2 чанки з цитуванням `[doc-02]`).
  - `get_document_by_id`: 2 мс (завантажено статтю обсягом 791 символ).
  - Загальний час сценарію застосунку (включно зі стартом процесу): ~1250 мс.

## 4. Порівняльний аналіз: що відрізнялося між двома підключеннями

| Характеристика | Підключення 1: Агент кодування | Підключення 2: Застосунок |
|---|---|---|
| **Призначення** | Дослідження репозиторію та надання контексту асистенту коду | Обробка запитів спортсмена та синтез тренувальних порад |
| **Клієнтська бібліотека** | MCP Client у середовищі агента (stdio pipe) | Типізований клас-обгортка `SportsJournalAppClient` |
| **Формат споживання результату** | Raw text / JSON string у блоці `content[0].text` | Структурований JSON (`structuredContent` або розпарсений `response`) |
| **Потреба в цитуванні** | Для формування посилання у чаті розробника | Обов'язкова валідація тегу `[doc-XX]` для картки атлета |
| **Обробка життєвого циклу** | Сесія тримається відкритим процесом агента | Чіткий цикл: `connect()` -> серія викликів -> `close()` |

## 5. Що довелося змінити та адаптувати в сервері

Під час реалізації двох різних підключень було виявлено та враховано такі технічні нюанси:

1. **Подвійний формат відповіді (`content` + `structuredContent`)**:
   - Агенти кодування за стандартом очікують масив текстових блоків `content: [{ type: 'text', text: '...' }]` для прямої передачі в контекст LLM.
   - Застосунку, навпаки, зручніше опрацьовувати валідований об'єкт TypeScript.
   - **Рішення в сервері**: кожен інструмент у `src/mcp/server.ts` повертає одночасно серіалізований `content` для агента і `structuredContent` для клієнта застосунку.

2. **Ізоляція робочої директорії (`cwd`) при запуску через child process**:
   - При виклику через зовнішній агент робоча директорія може відрізнятися від кореня репозиторію.
   - **Рішення в сервері**: резолвінг шляху до бази знань зроблено абсолютним: `path.resolve(process.cwd(), 'docs/lab2/data')`, а клієнт явно передає `cwd: projectRoot`.

3. **Стійкість до завершення процесу**:
   - Реалізовано коректне закриття `StdioClientTransport.close()` в обох підключеннях, що гарантує відсутність завислих процесів `tsx` у фоні.
